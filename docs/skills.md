# Task-derived skills

OpenSI stores per-user procedural memory, not model weight training. New terminal runs and existing historical runs are processed into reusable skills automatically. A background worker processes at most 25 historical runs per pass; the runner records new outcomes immediately. No additional model/API calls or provider credentials are required for learning.

Only an allowlisted topic/language vocabulary, recognized tool names, generated procedural sentences and aggregate outcomes are stored. Source prompts, file paths/bodies, model prose, terminal output, API arguments and secrets are never copied. This intentionally generalizes workflows rather than retaining arbitrary domain knowledge. Text-only or failed runs remain drafts unless an equivalent skill already has completed tool evidence. Completed tasks are not proof of business correctness.

Skills are deduplicated by user, topic, stack and tool set. Each new source run updates evidence counts and revision once. Successful steps replace the procedure; failed attempts do not overwrite a ready workflow. Before a new run, at most three enabled, topic/stack/capability-compatible skills are included as contextual reference in the agent prompt. This reaches compatible API/ChatGPT models and native Antigravity. A skill cannot add permissions, repeat old commands, or access another account. Current task instructions and approval policy remain authoritative.

UI: **Ko‘nikmalar** (`#/skills`) offers a global learning/applying toggle, search, steps, ready/draft status, evidence/use counts, per-skill enable/disable, forgetting and SKILL.md download. Forgetting is tombstoned so repeated tasks do not automatically reinstall the same recipe. Global disable affects future tasks; already-started model requests retain their original context. A task's progress panel identifies applied skills and learned outcomes.

Tables: `learned_skills`, `skill_learning_runs`, `skill_applications`. HTTP routes are authenticated, owner-scoped and use the existing mutation-origin protection. Schema migration is additive. Historical ingestion is idempotent; deletion/disable is preserved. The existing 100-slot orchestration limit remains unchanged.
