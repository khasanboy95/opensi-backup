# Bot tests before deployment

All root agents with terminal access receive `webhook_test` and `webhook_preview`; native CLI models receive the same actions through `opensi-actions.json`. Existing approval and owner scopes apply. The Terminal panel shows HTTP and invalid-secret test results. Connections > Deploy va API shows preview sessions, expiry, received-update status and a close button.

1. Implement `api/telegram.mjs` with `export default(req,res)` (handler mode), or a Node/Python server using `PORT` and GET `/api/health` (server mode).
2. Validate `x-telegram-bot-api-secret-token` against `TELEGRAM_WEBHOOK_SECRET`. Return HTTP 401/403 for an invalid header.
3. Run `webhook_test`. It starts a real child process, posts an invalid-secret request and a valid synthetic `/start`, records results, and kills the process tree. It never injects real bot/provider credentials.
4. With a saved Telegram connection, call `webhook_preview` open with entry/runtime/mode, requestId and duration (5–120 minutes). Successful preflight and HTTPS are required. An existing webhook is not replaced unless explicitly requested with replaceExisting. Polling must be stopped before switching to webhook.
5. The user sends a real Telegram message. The public HTTPS endpoint validates Telegram's secret header, invokes code inside the user's isolated project and returns the handler's JSON as the Telegram webhook response. Inspect status/Connections for received updates and errors; verify the actual reply in Telegram.
6. Close preview before permanent deployment/polling. Expiry prevents new execution and removes the preview webhook, preserving pending updates. Cleanup checks that the bot still points to that exact preview URL, so an already-changed permanent URL is left alone. A replaced older webhook is not automatically restored because its previous secret is unavailable.

Cloud webhooks are independent of the user's PC. Each request starts a disposable runtime with Docker network disabled. Node global `fetch` and Python `requests`/`urllib.request.urlopen` use a bounded stdio broker for public HTTPS. Direct sockets and other clients are not supported. The broker validates actual DNS connection addresses and every redirect, blocks private networks, strips sensitive headers across origins, limits requests to 32 (8 simultaneous), request bodies to 128 KB and responses to 2 MB. Jobs never receive the runner token, Docker socket or real bot token. Return reply JSON such as `{method:'sendMessage',chat_id:req.body.message.chat.id,text:'Salom'}`. Node Vercel-style handler and Node/Python HTTP server modes are supported. Persist state in project files/SQLite; globals reset each request. Local preview requires the online connector (`webhook_v1`).

For a user-requested always-running bot, `webhook_preview` open with `persistent:true` has no time expiry and no 500-message preview cap. It remains owner scoped and can be closed from Connections. It is still subject to server capacity, HTTPS request bounds and handler deadlines. Temporary sessions retain their 5–120 minute expiry. Always use the user's actual project and test its business command (e.g. `/news` retrieving nonempty RSS), not only a synthetic `/start` or a separate echo project. Passing handler tests does not prove business functionality or message delivery.

Telegram's response-to-webhook mechanism does not report the outcome of the requested reply method: https://core.telegram.org/bots/api#making-requests-when-getting-updates. A recorded HTTP 200 is handler evidence, not proof a user received a message. Duplicate completed update IDs are acknowledged without replaying the handler. A failed handler returns 503 for Telegram retry. Request bodies are bounded to 128 KB, replies to 32 KB, and each session to 500 distinct updates. Only update ID/status/reply method are retained in the session log; incoming chat content is not copied there. Local connector commands are owner-scoped.

Validation: real Node handler/server processes, invalid-secret rejection, failed handler/preflight, cancellation, owner isolation, replay protection, existing-webhook guard, expiry cleanup, real paired connector dispatch and Docker argument isolation. Telegram API calls in automated tests are mocked; live credentials and a real Telegram message are a separate boundary.
